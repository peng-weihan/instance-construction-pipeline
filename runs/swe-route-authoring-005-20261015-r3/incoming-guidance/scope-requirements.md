# 软工长程任务的规模要求：2026-10-15补充

本文件记录本轮用户对正在进行的出题审查的补充，不覆盖已有任务、评分或轨迹。

用户强调：长程软工任务应有足够大的真实工程量，参考 NL2Repo、ProgramBench、DeepSWE 的项目级任务；同时以 EdgeBench 原始软工题的任务规模、类型和真实工作内容为主要尺度。

本轮采用以下筛选原则：

1. 先确定产品或子系统的完整交付范围，再设计评分。优先完整系统构建、具有真实规模的行为兼容重建、多目标产品演进、跨模块/跨crate恢复；不因仓库很大而把单个小功能视为大型工程任务。
2. 记录求解者已经获得什么、实际还需实现什么。环境准备、作者写grader、完整仓库下载、构建等待时间都不计为求解者的工程量。
3. 按需求、API/状态/数据模型、模块依赖和端到端场景描述规模，不设未经校准的LOC/文件数硬门槛。合理的产品roadmap可以包含相对独立的真实需求，不能强行要求全部目标互相耦合。
4. 多次提交应对应可用功能逐步完整、兼容面扩大、集成错误减少或性能质量提高，而不是仅增加同构测试数量。完整参考、starter、普通强基线和近错消融的证据分别报告。
5. EdgeBench 中也有文件较少但优化深度很大的任务；这一分支必须有真实性能奖励、强基线和稳定改进空间，不能用停用的性能权重或理论上限代替。
6. 用户关于“不一定出成0～1那种题目”的补充，在本轮不解释为授权改写既有奖励：先把任务形态与单次pass/fail分开；原始指标可以是功能覆盖、QPS、周期、压缩率等，正式奖励表示另按有效任务要求配置。既有0～1奖励与旧曲线保持不变。
7. 对照原题时，分清公开JSON、实际镜像题面、论文描述和官方曲线；未取得的细节不补写。官方其他模型的曲线不能当作gpt-6.1-sol在新任务上的保证。
