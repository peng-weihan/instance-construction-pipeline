Implement an opt-in execution policy in HTTPX at the supplied fixed revision.

The complete production repository is at `/home/workspace/httpx/submission`. Edit its `httpx/` package; that package is the graded artifact. Keep the existing native API and behavior when the policy is absent. The starter already exports the public value objects, accepts the new constructor/send keywords, and passes ordinary upstream regressions, but does not execute the policy. This is a new extension, not a claim that upstream authentication, redirects, transport retries, or cancellation cleanup are missing.

A policy describes one logical `Client.send` or `AsyncClient.send`, including all physical sends caused by authentication, redirects, and retries. Convenience methods and `stream()` must reach this same behavior. Both sync and async clients must implement the same contract. Ordinary libraries, wrappers, subclasses and refactoring are allowed.

Public API and dispatch budget

- `ExecutionPolicy` is immutable, with defaults `max_attempts=4`, `replay_buffer_limit=65536`, `retry_statuses=frozenset({429,503})`, and `retry_methods=frozenset({'GET','HEAD','OPTIONS','PUT','DELETE'})`. Preserve the starter's validation and uppercase normalization.
- `Client(..., execution_policy=None)` and `AsyncClient(...)` default to legacy behavior. Their `send(..., execution_policy=USE_CLIENT_DEFAULT)` uses the client's policy. An explicit policy overrides it, and explicit `None` disables it for that send.
- An attempt is an entry into the selected transport's `handle_request` or `handle_async_request`. HTTP transport internal connection retries remain that transport's concern. Every entry, including an entry that raises, consumes one attempt. One budget is shared by all retries, auth challenges and followed redirects inside that logical send. A new send gets a new budget. Concurrent and nested sends must have independent state.
- Before a transport entry that would exceed `max_attempts`, raise `ExecutionBudgetExceeded`, a `RequestError` referring to the request about to be sent. No extra physical entry occurs. This also applies when the last permitted response is retryable: close that response, select retry, then fail the next budget check. Existing `max_redirects` remains effective as an additional bound.
- Retry a response only when its status is in `retry_statuses` and its request method is in `retry_methods`. Retry only `ConnectError`, `ConnectTimeout`, `ReadError`, and `ReadTimeout` raised before a response is returned by the transport, with that same method condition. Other errors, cancellation, and errors reading a returned response are not retried. There are no sleeps, clocks, jitter or `Retry-After` scheduling in this extension.
- A retry repeats the current physical request rather than restarting the original logical request or its auth flow. Retry responses never appear in `Response.history`, and auth never receives discarded retry responses. Normal auth/redirect history, cookies, mounted transports, method rewriting and response hooks remain native. Request/response event hooks run at the existing logical-hop boundary: request hooks precede the retry loop; response hooks see the final response of that hop.

Lazy bounded replay

- Do not eagerly read an iterable body to make it replayable. Its first physical transport consumption must remain streaming, preserve bytes/chunks, and may exceed the cache limit without failing that first successful send.
- An in-memory `httpx.ByteStream` is repeatable regardless of the limit. For every other stream, lazily retain at most `replay_buffer_limit` bytes while it is consumed. At the exact limit it remains eligible; if it exceeds the limit, discard retained data and mark it ineligible. A body is replayable after consumption starts only when the first iteration completed normally and all bytes fit. An unstarted stream may still be used after a connect failure.
- Apply the same replay rules to retry, body-preserving redirect and auth re-yield, including an auth request sharing the previous stream. Replays must use retained bytes without iterating the original stream again. If replay is required after partial consumption or overflow, raise `RequestNotReplayable` (`RequestError`) before entering the transport. Check budget before replayability if both would fail.
- A redirect that changes a request to GET uses the native empty body and is not blocked by the old body's overflow. Explicit pre-materialization by callers/auth before the first dispatch retains normal HTTPX semantics. A transport's call to `Request.read()`/`aread()` after the first dispatch must not bypass the policy's already established bound.

Origins and resource ownership

- An origin is `(scheme, host, effective port)`, with HTTP 80 and HTTPS 443 defaults. Before every physical transport entry, remove `Authorization` and `Proxy-Authorization` if that request's origin differs from the initial request's origin. Do this after request hooks, even when a custom auth flow or hook reinserts credentials. Preserve same-origin authentication. Keep native redirect header/cookie rules in addition to this opt-in restriction.
- Close each discarded retry response exactly once, before any next transport entry; never drain its body merely to retry it. If close raises (including cancellation), propagate it without retrying. On other failure paths retain native response and auth-flow cleanup.
- For `stream=False`, a final response read failure closes that response and does not retry it. For `stream=True`, returning headers leaves final response consumption/close with the caller. Trace termination describes send returning, not the later lifetime of a user-owned response. Cancellation must propagate with cleanup and trace; later sends must work independently.

Structured execution trace

- On every policy-enabled successful send, store an immutable `ExecutionTrace` in `response.extensions['execution_trace']`. On every exception escaping a policy-enabled send, attach it as `exception.execution_trace`. Disablement introduces no trace. Do not leave mutable internal state on requests or clients that can contaminate another send.
- `ExecutionTrace` has `attempts: int`, `events: tuple[ExecutionEvent,...]`, and `to_dict()` returning JSON-compatible dictionaries/lists. Each immutable event has exactly `kind`, `attempt`, `method`, `origin`, `status_code`, and `error_type`. Unused optional fields are `None`.
- Emit `dispatch` immediately before a physical attempt (attempts numbered from 1), then `response` for a returned transport response or `transport_error` for an exception escaping that transport entry. Emit `retry` after closing a discarded retry response, or after selecting retry for a transport error. Response/retry events carry the response status; transport-error/retry events carry only the exception class name. There is exactly one final `return` or `error` event, carrying the final response status or escaping exception class name. Each nondispatch event uses the current cumulative attempt number, and the method/origin of the request it describes. Budget/replay errors produce a terminal error without a new dispatch. Post-response read errors produce a terminal error without a transport-error event.
- Origins in events are ASCII strings such as `https://a.test:443`, `http://a.test:8080`, or `https://[::1]:443`. Never include userinfo, paths, queries, request/response headers, bodies, exception messages, or timestamps. No event callback is required.

Development and grading

Run `python -m pytest -q development_tests` in the submission directory for public examples, and use the included upstream tests for compatibility. A frozen private verifier invokes the actual HTTPX clients with independent scripted native transports. It observes dispatch/body/close behavior externally, including sync/async boundaries, and separately checks trace semantics. Seven semantic groups have equal weight: budget, replay, origin, events, cleanup, compatibility, native regressions. Within each group, passed frozen members / total frozen members gives partial credit; the total is their weighted sum. Performance is not scored. Correct behavior in one group can earn credit before other groups are implemented. Invalid candidate syntax, missing files and candidate timeouts are scored failures; verifier infrastructure failure produces no numeric score.

Only `submission/httpx/**/*.py` and `submission/httpx/py.typed` enter grading; do not edit authoritative tests or try to write rewards. Dependencies are preinstalled offline. The intended working budget is 21600 seconds; this budget is not evidence that the task requires six hours.
