# 难度判断：held_for_evidence

本实例已经构造成真实 CRoaring 扩展，但不是六小时难度已验收题。普通现成 API 组合完整解决合理语义合同，这是实际否证证据，不能藏掉或禁止这些 API。starter 与 reference 当前均为 0.40；其余 0.60 性能分尚未启用，所以当前分数没有区分优化质量。这一草稿不能直接启动正式训练并期待长期涨分。

最强已测便宜基线是未修改固定引擎的 `-O3 -march=native` 构建、保留 dispatch、run_optimize、从三个两两交集选择最小的一个以求三重交、批内相同查询复用。还测了原版普通 Release flags、run_optimize 开关，以及加复用前的组合。证据分别在 ordinary-baselines、strong-dedup-baseline、final-paired-probe。参考不是独立 cheap solution；near-miss 控制也只是基线的明确变异。

在 AMD Ryzen 9 9950X / GCC 13.3.0 主机，三轮配对、已带批内复用的 benchmark 中，普通/融合的中位数加速比分别为 dense 18.91、sparse 0.70、run 0.40、mixed 1.56、window 4.44。具体 ns/query、原始样本和 checksum 见 host-benchmark-summary.json。此主机未锁核/独占，另一次带 RSS 采集的测量与这些数值明显不同，因此这些结果只证明值得继续研究的热点，不是可移植的奖励锚点。旧的未去重加速比也保留，不能挑最快样本替换较强基线。

两条真实后续路径：

1. 用表示与密度选择算法：array 采用有序三路归并或小集 membership 查询，run 采用区间端点 sweep，bitset 采用融合 popcount；处理缺失 high-key 与窄窗口时跳过无关存储。产物仍是同一个 C ABI 与原生 kernel，反馈应来自分组吞吐和内存，而不是加测试数量。
2. 减少重复 work 并保持架构一致性：在批内识别重复三元组/重叠窗口，组合 key 目录遍历与只读 COW 容器访问；针对 x86 向量 popcount 和 ARM/scalar 路径选择实现。需要保证区间两端、65535 高 key 和未命中容器下的 bin 0 正确，且构建/输入内存成本不劣化。

早满风险很高：朴素公开算法就能做对所有功能；直接稠密化、编译器自动向量化和批内去重已经产生大幅进步。八格统计本身不证明六小时，添加更多相似 case 也不能改善这一点。融合参考在 array/run 已慢于强基线；一个简单的表示分支甚至可能快速吃完剩余空间。正式性能分尚无真实目标平台强参考包络、噪声和高分可达证据。

最便宜的剩余否证是：在目标平台上对普通组合、独立迭代器组合和按容器类型选择的简单混合策略，使用固定公开 workload、锁定编译参数与核亲和性各重测至少五轮，检查优势是否大于测量噪声。如果普通工具或简单策略已稳定支配，就拒绝此性能候选，而不是扩大数据规模或削弱 baseline。只有这个筛选后，才值得另行修订启用性能公式，随后按用户安排做 ARM 和正式六小时校准；本轮没有启动教师。
