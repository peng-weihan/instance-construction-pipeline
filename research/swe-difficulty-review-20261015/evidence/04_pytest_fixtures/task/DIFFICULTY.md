# 难度是待验证假设

最强已实测廉价路线是公开 hook-only baseline：使用 setup wrapper、
post-finalizer、makereport 和不可变 observer，就能取得 12/24 检查、0.50。
它与更早的独立普通插件探针均保留。尚未构造独立的“插件包装内部方法”强解；
不能因为常规 hooks 本身没有缓存通知，就声称只能修改 core 或需要六小时。

继续改进的两个具体方向：
1. 把解析身份和实例 generation 分开，在 per-item shortcut 与跨 item cache
   比较之间保留正确依赖边；处理同名 override、动态请求、缓存异常以及比较
   抛错的参数，不额外调用 __eq__/__repr__。
2. 将失效原因和 callback 生命周期贯通至依赖级联与 scope 调度，保留失败后
   的全部 LIFO cleanup、原生异常分组、post-finalizer 的缓存可见性，并让
   observer 重入和最终 report 始终与事件流一致。

这些方向共享状态和异常路径，具有连贯工程价值；它们的数量、代码行数和
测试数都不是长时难度证据。参考由一个作者在构造过程中完成，暴露明显的
早期饱和风险：一个熟悉 pytest 的模型可能很快通过包装原生方法做完协议。
六小时潜力目前没有轨迹证据。包内 intended budget=21600 不代表已通过难度。

最便宜的后续否证：只给公开题面与 starter，独立实现一个允许使用内部方法
包装的插件方案，在相同快照评分器重放。如果迅速接近满分，应 hold/reject
本路线的六小时训练价值，而不是禁用插件或增加无关功能。此工作本轮未运行，
也没有启动任何教师。剩余门禁为镜像/Harbor 双入口实测、ARM、权限的镜像内
复验、独立语义审阅及正式六小时校准；静态包/Oracle=1 均不能替代。
