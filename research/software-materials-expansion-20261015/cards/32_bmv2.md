# 32 · BMv2：编译后包处理程序执行系统

- 路线：M2 规格驱动系统；优先级 `build_scope_probe`，先判断 IR 语义与工具链边界是否可控。
- 固定版本：[7f4e1daca12b7fe52897687764b7e74ded7dab55](https://github.com/p4lang/behavioral-model/tree/7f4e1daca12b7fe52897687764b7e74ded7dab55)。完整文件树未截断；源码片段及 SHA-256 见 `sources/32_bmv2/manifest.json`。
- 已有能力：上游已是读取 P4 编译器 JSON 的参考软件交换机；不是待新增 interpreter，也不宣称生产性能。
- 拟题完整子系统：新 starter 给离线包输入/输出、JSON parser 和控制命令框架，实现编译后程序加载 → header/metadata 表示 → parser 状态机 → match-action 管线 → stateful registers/counters → checksum/deparser → 输出包及端口。
- 边界：明确 JSON 版本/feature manifest；支持定长/变长字段和栈、位宽表达式、exact/LPM/ternary、直接动作及上述状态；先排除 action profile、meter、clone/recirculate、多播、extern 插件、gRPC、真实 NIC。未承诺完整 P4/v1model。
- starter 尚未制作；采用 BMv2 思路重新抽取的有界系统规格，不把现有功能冒称缺口。必须接受 manifest 内任意合法组合，不能仅支持某个示例路由器。
- 状态链：JSON 引用/位宽校验 → packet bits/有效 header → parser 路径及错误 → 匹配键/优先级 → 动作/元数据/寄存器 → 后续表选择 → checksum → 有效 header 序列化及未解析 payload。

- 组合场景 1：同一输入经过 VLAN/IPv4 可变头解析、LPM 与 ternary 优先级选择、字段改写，再输出精确字节与端口；检验表示之间的一致性。
- 组合场景 2：多包共享 register/counter，控制命令更新或删除表项后继续处理；验证状态仅按规定时点影响后续包，默认动作/overflow 仍一致。
- 组合场景 3：短包或 verify 失败进入错误元数据路径，后续控制逻辑选择 drop/继续；与无效 header 发射、payload 保留组合，避免错误一律自动 drop。
- 初版完成后的改进假设 A：基本转发通了以后，补齐非字节对齐位宽、符号/截断、栈/变长 header 和跨阶段 metadata，消除表示漂移。
- 初版完成后的改进假设 B：静态单包通了以后，补齐动态表项生命周期、跨包寄存器/计数器和 parser 错误路径，形成完整可编程执行系统。
