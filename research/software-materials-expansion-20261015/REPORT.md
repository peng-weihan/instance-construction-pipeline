# 软件工程出题素材池：50 个来源与筛选结论

调研日期：2026-10-15。

**本批从 15 个扩充到累计 50 个主仓库，新增 35 个，五条构造路线各 10 个。** 从 [50 项总目录](CATALOG_50.md) 浏览，并用 [CSV](candidates.csv) 或 [JSON](candidates.json) 筛选。素材 ID 延续此前登记的 28–77；另外提供连续目录序号 1–50。

核验了 **50 个固定 commit、50 份未截断文件树、435 份关键源码/文档/测试/许可文件，以及 212 个证据位置**。选读文件共 13,830,994 字节；已检查文件字节数、SHA-256、证据行位置和本地链接。主仓库与本次检查的既有登记没有重合，见 [去重记录](previous-source-check.json) 和 [完整性结果](inventory-check.json)。这表示材料库存完整，不表示已经完成完整仓库审计或构建。

## 初筛结果与下一步投入

**23 项建议先做范围验证，27 项暂缓并先消除关键疑问。** 其中 10 项需排查现有能力和范围价值，10 项性能来源等待强基线，3 项等待包装基线，2 项等待可重复测试判据，1 项待范围收敛，1 项待离线工具链。优先级记录在每张卡和结构化登记中；build_scope_probe 表示值得研究，不能直接等同于可出正式题。

可以优先从以下完整工作流中选材。表中仍是待验证设计，没有声称上游缺少这些能力。

| 方向 | 交付目标与可能的复杂性来源 | 最先验证什么 |
|---|---|---|
| tox / Task / APISIX | 测试矩阵资源租约与恢复、任务工件缓存、配置包预检/激活/回退；涉及身份、依赖、失败和生命周期 | 原生插件、文件锁、现有缓存或配置工具能否直接完成整个范围 |
| Thrift / Cap’n Proto / Flecs | 多文件 IDL 与反射、动态 schema 与演进、延迟世界修改和观察者一致性 | 区分规格驱动构建与实现恢复，先确认健康参考、真正缺口和独立判据 |
| NATS / Mosquitto | 持久消息、消费者重放、会话与投递状态；跨连接、确认、过期和恢复 | 现成服务加薄适配能否完成；拟 starter 需要什么实质实现 |
| Nushell / Jinja / Pydantic Core | 结构化管线和闭包、模板继承与作用域、联合分支选择与序列化 | 恢复点是否形成关联语义链；单点补丁能否绕过整个工作流 |
| Helix / Tantivy | 多选择区事务与分支历史、索引提交/删除与 reader 生命周期 | 用确定性操作序列验证历史、可见性与失败后的状态 |
| yq / restic / Miller / Rsync | 配置更新、快照备份恢复、跨记录 DSL、目录同步；保留跨步骤状态与输出兼容 | 普通库和现成工具组合是否已完整覆盖；避免只剩 CLI 参数映射 |

性能 10 项全部暂缓，先测默认配置、最佳合法配置和现有算法路径。工作负载必须保持相同正确性、持久性及资源约束；LMDB 的弱同步不能与强持久基线直接比较。没有测得收益前，不设臆测性能端点或长程时间估计。

## 当前源码排除了哪些误判

下列结论来自固定版本的实现或测试；素材卡保留对应上游链接和本地证据。

- **Hatch 已有锁文件体系。** PEP 751、pip/uv locker 和矩阵共享输入合并已经存在；新增锁文件支持不足以成为产品目标。离线交付包也要先与插件和缓存方案比较。[素材卡](cards/44_hatch.md)
- **Fastify 已有 handlerTimeout 和 request signal。** 需要评估的候选目标是插件作用域预算、排队和资源清理组成的执行策略；普通超时功能不能冒充缺口。[素材卡](cards/46_fastify.md)
- **CEL-Go 当前实现不能从旧别名壳推断。** 已获取 canonical 仓库的环境、检查和执行代码；parse/check/eval 本来就存在，保持暂缓。[素材卡](cards/55_cel_go.md)
- **fast_float 已处理非默认舍入环境。** 当前快路径明确区分舍入环境，不能把旧 README 的简化前提当作当前实现缺陷。[素材卡](cards/60_fast_float.md)
- **yq 已有相对赋值和 anchor 状态。** 研究价值在多文档、表达式更新、源结构和输出行为组合的兼容边界；基本 YAML 读写不够。[素材卡](cards/72_yq.md)
- **DuckDB 已有聚合状态溢写回归，Sphinx 已有扩展失效机制。** 继续遵守首批的强基线判断，不把成熟能力重新包装成待实现功能。[首批分析](REPORT_15.md)

这也解释了为何没有把 50 项全部列成推荐出题：一份有用的素材卡应当能指出该方向何时值得停止。

## 来源身份、许可与独立性

主仓库登记已处理 dbt、CEL-Go、Pydantic Core 的迁移：分别使用 dbt-labs/dbt、cel-expr/cel-go 和 pydantic/pydantic。dbt 区分当前主线与旧 Python 系列；Pydantic Core 使用单仓中的实现。旧别名或迁移材料只作证据，各只计一个主来源。Tantivy 沿用已核对的 quickwit-oss/tantivy。

50 个主仓库不同，也不等于 50 个独立任务族。Thrift/Cap’n Proto/Avro/FlatBuffers 存在 schema 与 RPC 谱系联系，数据工具存在表达式和格式处理重叠，Jinja/SQLFluff/dbt 存在依赖联系。后续训练/评测划分应记录源码、协议、算法、行为和测试生成谱系，不能只按项目名或 seed 拆分。

许可逐项保存和记录。LZ4 库与工具、cmark-gfm 代码与部分测试文本不能统一按一个许可处理；Rsync、libvips、Pandoc、Wireshark、LMDB 等各有具体许可文本。纳入 starter/reference/test 前，按实际文件及依赖继续清点。

## 素材到正式题的推进方式

每张卡均提供拟交付范围、已有能力、端到端场景、至少两个后续工作假设、正常基线、首个否证探针、独立判据和离线风险。下一步先筛完整交付目标，再做健康参考和低成本基线；通过后才构造 starter、隐藏分布与评测器，最后做真实长程难度校准。

复杂性应来自表示转换、跨模块语义、状态/历史、失败恢复、兼容性和正确性约束下的优化。不能用文件数、代码行数、任意禁库、构建等待或额外无关需求硬抬难度。

本次没有新增题包、运行候选基准、启动模型或给出六小时难度验收。保存的是定向选读文件与完整文件树索引；完整源码 checkout、离线依赖包和健康参考运行仍需在选定范围后完成。迁移旁证文件不计入 435 份主来源文件。
