一、征集什么
我们征集一批用于长时程 agent 评测的任务，首批 100 题。一道题要支持这样的运行：模型在一个隔离环境里连续工作数小时，期间反复提交中间结果、拿到评分反馈、继续改进，最终成绩取一次运行中所有提交里的最好一次，而不是最后一次。
衡量的是给足时间之后能做到多好，不是一次性准确率。核心产出是一条分数对交互时间的曲线。一道题有没有价值，就看这条曲线画不画得出来，本文的技术规格基本都是围绕这一点展开的。
设计参照是公开的 EdgeBench 及其 SForge harness（ByteDance-Seed/EdgeBench，Apache-2.0）。公开的 51 道题可以直接拿来看形态。收题走 Harbor 格式，具体的目录结构和命名规则我们会随合同一起给。EdgeBench 是参照而不是第二种格式，下面所有要求最终都落在 task.toml 的字段上。
有一点先说在前面：下面绝大部分要求在镜像构建的�_optimization、k12_math_recommendation、college_english_exam_bank
组合优化	12%	按解的质量而不是对错打分的困难搜索与分配问题：路径规划、装箱与排样、划分、图着色，以及求解器本身的构建。	vehicle_routing_time_windows、jagua_nesting_optimization、tree_block_partitioning、smt_solver
形式化数学与定理证明	10%	面向形式化目标的机器证明，以 Lean 和 mathlib 为主。	pfr_formalization、sphere_eversion_formalization、carleson_formalization、lean_analysis_proofs
交互式游戏与模拟器	9%	长时程 agent 通过 API 驱动实时游戏或模拟器，按一段较长会话中取得的结果打分。	nethack_dungeon_agent、wesnoth_tactical_ai、openttd_transport_ai、anchorhead_text_adventure

三、环境规格：agent 与 verifier 必须分开
这是全文最硬的一条，也是第四节那些属性能成立的前提。
每道题交两个环境：agent（工作）环境，模型在里面干活；verifier（评判）环境，给提或者靠单一共享上下文里的文件权限做的隔离，我们光读交付物确认不了；而且 harness 以 root 跑 agent 时，权限那一套直接废掉。
4.Dockerfile 和构建上下文必须交。预构建的 OCI image layout 是欢迎的附加项，有且无误时我们会直接拿它跑，但它不替代源文件。我们保留从源码重建并比对的权利。这两样出题方本来就有，一起交上来除了上传不多花成本。
5.agent 和 verifier 两个作用域都禁网：agent 干活时不上网，verifier 打分时也不上网。三个作用域都按规范指定的 Harbor 网络策略格式声明。environment 作用域在镜像构建需要拉包时可以设为 public，但要在 open_internet_justification 里写明原因。不管构建期怎么设，运行中的容器一律不许发网络请求；第六节的 digest 固定，就是让用到网络的构建仍然可复现的手段。
6.verifier 无状态，每次提交调用一次。不要做常驻的评判服务。我们成最后评一次。
•网络隔离以它为前提。 EdgeBench 跑 work 容器时，出站白名单只放 judge 端点和模型 API。只有打分的一方在边界另一侧，这条边界才有意义。
•公开题集就是这个形态。 51 道公开题全部以镜像对交付：edgebench.work.<task_id> 和 edgebench.judge.<task_id>。单镜像的题我们收不了，上面这些评测行为对它一条都不适用。
四、可评测性：一道题必须具备的五项属性
环境分开是必要条件，还不够。下面五项属性题目必须具备，交付材料里也要写清楚。其中第 2 项和第 5 项最要紧：它们只能在出题的时候做进去，交上来之后我们既查不出也补不了。
#	属性	题目要保证什么	为什么
1	提交可快照	分数完全由一组明确的文件决定，这组文件以 submit paths 或 artifacts 目录声明。分数不能有任何一部分依赖 agent 环境里的活进程状态。	每次提交都是拿这些路径打成的归档包去�打分命令本身，启动和灌数据在它之外，所以光看这个数会低估一次提交的真实成本。
5	verifier 输出是结构化的	不能只吐一个标量。至少要有：总分、有效性标志、一组带 pass/fail 的具名检查项。同时说明这份输出该怎么读，我们才能把它解析进这几个字段。	EdgeBench 每次提交后会把通过率、分数、失败项名称和一段摘要返回给 agent，agent 就是靠这些诊断信息改进的。只给一个数字，agent 不知道该修哪里，曲线会因为和模型能力无关的原因压平。在我们这边这是硬要求：分数必须和有效性标志一起到达，解析不成这个结构的输出算评分失败，不是得低分。

学习曲线成立的条件
机制之外，题目本身得是能随时间学起来的。下面几点入库时逐条看：
•agent 预算要长。 按小时算，不是按分钟。低于一小时画不出曲线，直接拒。3 小时是能接受的下限。EdgeBench 支持连续�ry。另外两种都不行：binary 把题压成 pass/fail，没有曲线可测；unbounded_continuous 题与题之间不可比，没法汇总。最常见的失误是漏写字段，因为默认值静默生效。
•评分公式和它的每一个常量都要进机器可读的元数据，不能只存在 verifier 源码里。只以代码字面量形式存在的常量，不读 verifier 就没法校验、没法编版本、也没法讨论。
•直接给归一化之后的分数，同时给原始指标。 一条要我们在自己这边重新实现一遍的自定义归一化曲线，就是两边数字对不上的源头。
•声明分数方向（越高越好还是越低越好），并保持单调：不允许做负面操作还涨分。
•逐题给出基线和上限，整批只用一种机制。 一次交付里出现两种机制，任何只读其中一种的系统都会把另一半题报成未评分。
五、随题交付的材料
5.1 确定性证据
上一节第 2 项是最容易“想法上成立、实际上不成�这是完全可以的答案。不能接受的是交一个什么都不干的参考解文件，见第七节。
•一张分数表，逐题给出 oracle 分值、nop 分值，以及至少一个前沿模型跑三次以上的平均分。每道题三个数。有了这张表，我们才能确认自家 harness 复现得出你们的数据，也才能判断声明的奖励端点是不是真端点，还是只是指标的边界。
•参考运行提交了多少次。 十二小时里提交一百次的参考运行，和只提交一次的，可能报出同样的分数，含义完全不同。没有这个数，参考分数和我们跑出来的结果对不上。
优先项： 同一个模型在三个或更多交互检查点上的成绩，比如 2 小时、6 小时、12 小时。这正是公开的 EdgeBench 附录对全部 134 道题给出的逐题数据，也是交付前唯一能证明题目确实随时间变好、而不是平坦、饱和或者根本做不出来的证据。有了曲线，上面那张表自然就有了。
5.3 �平台专属的镜像。digest 固定错了这两条要求就会打架：linux/amd64 的镜像 digest 在 x86 上解析得开，在 ARM 上会失败，看着像固定的问题，其实是架构的问题。固定 manifest list 的 digest，两条一起满足。浮动 tag 两条都不满足，今天做的确定性检查对六个月后的同一道题说明不了任何事。
•如果题目固定了 gpu_types，说明它在哪些加速器上验证过，以及评分是不是在 GPU 上执行。绑死在单一加速器系列的题，不管镜像支持什么，实际上都是单平台的，这个取舍要在开工前谈定。
•如果还交了预构建的 OCI image layout（可选），它内部必须自洽：同一个 digest 在 index、manifest 和 image config 里的每一处声明都要一致，index 引用的每个 blob 都要在 layout 里。一旦 layout 成了我们真正跑的东西，这就是唯一能用的完整性检查。layout 同样要带两种架构。
