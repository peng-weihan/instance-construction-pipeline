# 难度假设与反证

当前选择结论是 **held_for_evidence**，交付为有实现、有本地证据的 constructed_unverified 草稿。没有启动任何教师或六小时 rollout；Oracle=1 不表示难度通过。

最强实际廉价基线保存在 job `controls/cheap/`：把 NDJSON 映射到现有 JSON 属性解析器（也可用上游 `content_type_overrides` 达到相同别名效果），只加 contextlib + HTTPX iter_lines/aiter_lines 的端点包装；同时修掉会遮蔽功能测试的 required multi-media body/import 小问题。没有禁止成熟库、复用现有模型转换或 template overrides。这份基线实际取得 **0.60、21/36**：它已解决分块 UTF-8、空行、末记录、正常/异常关闭、同步异步和自然的背压。此分数意味着早期饱和风险很高，不能宣称首小时增长合格。

剩余两个有产品意义的改进路径为：

1. 把流式响应纳入真实 parser/endpoint 元数据，得到确切返回注解和 documented-success/media 检查；在进入 context 时、零消费时、异常/取消时保留响应所有权，并用真实 wire gate/EOF 复核。仅正常消费通过还不够。冻结产物是 parser/模板源码和生成 SDK 的生命周期 traces。
2. 在共享 client 上按 operation 解析安全性继承、显式匿名、可选认证；在合并 defaults 后去除当前请求凭据而不污染其他请求，同时保留 JSON/multipart body 编码和必填签名。冻结产物是生成器源码、headers/body wire trace 和原生回归。

这些是后续改进方向，不是“每条需要数小时”的预测。完整参考目前只需五个生成器文件的实际改造，绝不能以项目文件数、测试数量或 UTF-8 边界数量反推六小时难度。普通 HTTPX 已处理大部分流控和取消，联合合同的自然剩余也可能很快被一个模型完成。两个近错控制（认证不覆盖、预读整个响应）有可解释的部分分，但同样不能证明长程学习曲线。

最便宜的剩余否证是：在下一阶段给获准的同一模型这个完整公开任务，明确允许最小包装基线和上游配置，然后测真实早期完成情况；若常规模板/安全性小改动迅速满分，就拒绝此版本作为六小时训练题，不增加无关功能、复制 schema 或重设权重挽救曲线。正式六小时和三轨迹均分规则属于后续校准；当前用户要求不启动它们。先做 ARM/原生 Harbor 的打包运行检查也只能验证可执行性。

固定 schema 是一个工作负载，不是广泛 SDK 产品兼容性证明。评分按语义组平均，组内测试相关性和某些联合行为的依赖可能使进步阶梯较大。取消和 wire gate 的 timeout 是错误终止上限，不是性能目标；重评分保持源码/依赖/规格和 oracle 不变，结果按同一权威 grader 产生。
